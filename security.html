Security

How RegAnchor protects organisation data. Last updated 14 August 2026.
In short

RegAnchor is a multi-tenant portal. Each organisation’s registry is isolated by Postgres row-level security. Access inside an organisation is role-based. Professional plans include five named seats.

Section 01

Authentication

Users sign in with a work email and password, or with Google single sign-on where that provider is enabled for the workspace. Sessions are issued by Supabase Auth. The browser only ever holds a publishable key — never a service-role secret.

Invitations are emailed as a one-time link. The token is stored hashed; it expires after 14 days and can be revoked. The invitee must authenticate as the invited address.

Section 02

Role-based access

RoleWhat they can do
OwnerBilling, membership, and all registry actions. One per organisation.
AdminInvite colleagues, assign roles, edit systems. Cannot remove the owner.
EditorRegister and update AI systems, controls, and assessments.
ViewerRead the registry and reports. Cannot change records.

Role changes run in the database, not as a client-side field edit, so a user cannot grant themselves owner access from the browser.

Section 03

Seats and tenancy

Essentials is a single named seat. Professional includes five seats (accepted members plus pending invites). Seat limits are enforced when an invite is created.

Queries for systems, members, and invitations are scoped to organisations the signed-in user belongs to.

Section 04

What comes next

Enterprise customers can expect SAML / OIDC against their own identity provider (for example Microsoft Entra ID or Okta), optional SCIM, and a searchable organisation-wide audit log. Governance events are already written to an immutable audit table today.
